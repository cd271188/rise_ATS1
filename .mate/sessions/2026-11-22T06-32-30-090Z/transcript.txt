# Agent environment setup

Use this skill when initializing or repairing the agent workspace, installing dependencies, starting development servers, or preparing tests. Inspect the repository's actual runtime, lockfiles, setup scripts, Dockerfiles, environment examples, and Compose files first. Run the main application natively in the agent container; use supporting Deploymate services when required. A persistent project deployment is a separate task handled by the `deploymate` skill.

Use the project-scoped `deploymate` MCP server for dependencies. Read the tool schemas, `list_service_types`, and `list_instance_types` before provisioning. The saved session fixes the authorized project and credentials. Do not substitute another project or copy credentials from unrelated services.

## Create session-specific supporting services

Use the Deploymate MCP tools to provision the missing services needed to run the current application or its tests. This applies whether dependencies are declared in Compose, source code, environment variables, setup scripts, or documentation. An authorized environment-setup task includes creating its required session dependencies through the normal tool approval flow; do not stop at suggesting that the user create them manually when the tools can do it. Keep the main application running natively in the agent container.

1. Identify the required dependency graph and briefly state which services will be reused or created before provisioning. Inspect `list_services` for regular project resources and `list_created_services` for this session's resources. Prefer compatible development/test resources; do not run test migrations, reset databases, or write test data against production dependencies merely because they are reachable. If safe reuse is unavailable, create an isolated session dependency.
2. Read `list_service_types` and `list_instance_types`, select the appropriate service kind and valid resource-plan IDs, and call `create_service` with explicit `lifecycle="session"`. The server supplies the calling session's project; do not set another project or substitute credentials. Use distinguishable dependency names and record returned IDs immediately so a failed setup/retry does not create duplicates.
3. Create storage first when using reusable volumes, then foundational services such as databases/caches, then source-backed supporting APIs/workers. Each new dependency and volume created for this setup must use session lifecycle. Session services are tagged to the calling agent session and suspend on session completion; suspension is not a promise that data is deleted or capacity is immediately released. Do not attach a session resource to a persistent production deployment.
4. For a source-backed dependency, discover the actual repository through `search_service_repositories` on the current service, inspect its files/branch with the repository tools, and supply that provider/repository plus a usable Dockerfile and actual configuration. Do not invent a direct-image creation field: custom images require a repository-backed Dockerfile where the current schema requires source. If source preparation is outside the permitted setup scope, report the missing Dockerfile/source requirement rather than editing unrelated application code.
5. Wait for build/startup readiness, inspect bounded logs, then read `get_service_connection` and `get_service_environment`. Use the returned endpoints and credentials in the authorized native application environment; replace Compose hostnames and localhost dependency addresses. For existing remote consumers, read and merge their complete environment before `update_service_environment(deploy=false)`. Keep credentials secret and verify that the dependency's network access permits the agent or consuming service.
6. Run development migrations only against the intended development database, then start and verify the native main application. Check an authenticated dependency operation as well as the application's health endpoint. Record dependency IDs, lifecycle, endpoints without credentials, and verification results in the setup handoff. On failure, report existing resources and the actionable blocker; do not repeatedly create services or delete pre-existing data.

### Available service types and when to use them

`list_service_types` is authoritative for current fields and support. Choose among these kinds according to the dependency's actual requirements:

| `kind` | When to use it during agent setup | Important configuration |
| --- | --- | --- |
| `postgres` | PostgreSQL required by the application's ORM, migrations, or integration tests | Use supported database/version/extension options and valid database resource plans. Read generated credentials and the reachable endpoint; do not substitute SQLite. |
| `valkey` | Compatible Redis-style cache, queue broker, sessions, or key/value dependency | Match eviction and persistence needs. Verify command/module compatibility and authentication before replacing Redis. |
| `redis` | Legacy creation alias when a Redis-compatible dependency is intended | Creates Valkey; it does not supply Redis-specific modules or a different Redis engine. Prefer the explicit `valkey` kind. |
| `stateful` | Custom persistent engines such as MySQL/MariaDB, MongoDB, ClickHouse, or a small MinIO dependency | Use a verified image via a repository Dockerfile, the engine's real port and data path, `storageGB`, and `storageMountPath`. Keep a standalone engine at one instance with `autoScaling=false`; do not pass reusable `volumes` to stateful creation. |
| `private` | A separate internal HTTP API, search gateway, mock server, or other network dependency with available source | Use its actual port/health check and internal endpoint. Attach supported session volumes if durable files are needed. Prefer this for internal dependencies that do not require public access. |
| `web` | A separate supporting HTTP service that actually needs a public endpoint, such as a required callback receiver | Configure the supported public endpoint and health check. Do not deploy the main application here just to finish agent setup, or expose an internal database as a web service. |
| `worker` | A separate continuously running consumer or background processor needed by the test/development workflow | Configure actual source/start behavior, dependency endpoints, concurrency, and readiness signals. Use `worker` as the MCP kind even though service records may call it `job`. |
| `cronjob` | A scheduled supporting task whose execution is necessary for the requested environment | Inspect the schedule semantics and avoid unintended repeated work. A one-time migration normally runs natively after database readiness instead. |
| `volume` | Persistent files shared/mounted by supported remote web/private/worker/cron services | Create explicit capacity first, then attach using `configuration.volumes=[{"volumeId": ID, "mountPath": "/data"}]`. A volume is not a running dependency or object-storage endpoint, and is not automatically mounted into the agent container. |
| `codebase` | Repository context for an authorized agent task that prepares a missing supporting component | Has no running process or CPU/RAM plan. Creating it alone cannot satisfy a network dependency; provision a runtime kind when required. |

Creation call shape (illustrative placeholders are not executable values):

```text
create_service(
  kind="<required kind from list_service_types>",
  lifecycle="session",
  configuration={...actual required fields and valid IDs for that kind...}
)
```

For example, a native API requiring PostgreSQL, Redis-compatible queues, and a separately sourced internal API can use a session `postgres`, a session `valkey`, and a session `private` service. Reuse compatible session instances, wait for each prerequisite, inject their real connection values, and start the main API natively only after dependency checks pass. Create only the components that the requested environment actually uses.

## Agent environment: Docker is prohibited

**Docker is not allowed in the agent environment. Never run `docker`, `docker compose`, or `docker-compose` there, including build, run, up, and config commands.** Do not install or start a Docker daemon, mount a Docker socket, request privileged containers, or substitute another local container runtime to work around this restriction. Creating a Dockerfile for Deploymate's remote build pipeline is allowed; executing it locally with Docker is not. Run application code and native checks directly in the agent environment, and use Deploymate services for containerized dependencies.

**When any Docker Compose file is found, divide its required components into the main application and supporting Deploymate session services. Create or reuse the required session services FIRST, wait for them to be ready, then start the main application natively inside the agent container. Never run the main application through Compose or create a remote application service merely to complete agent environment setup. Do not execute Compose or stop at reporting that Docker is unavailable.**

1. Inspect `compose.yaml`, `compose.yml`, `docker-compose.yml`, or `docker-compose.yaml`, including referenced overrides, profiles, environment files, and wrapper scripts. Read the YAML without invoking Docker. Identify each required service's image/build, command, container port, environment, dependencies, readiness checks, and storage needs. Identify the main application from the repository and the requested setup; its Dockerfile and Compose command describe the native runtime setup and start command to reproduce in the agent container.
2. List existing project services and `list_created_services`, and reuse compatible resources. Provision missing supporting Compose components with `create_service` and explicit `lifecycle="session"` for agent setup, development, and tests. Map PostgreSQL to `postgres`, compatible Redis/cache services to `valkey`, other supported database images to `stateful` with engine-specific persistent storage, and supporting application/worker components to supported web, private, worker, or cronjob services. Keep the main application in the agent container for environment setup; use its repository source, native dependencies, and start command. For other images, use a Dockerfile-backed service only when the supported creation schema can represent its requirements; report an unsupported dependency precisely instead of substituting an incompatible service or launching a local container.
3. Reproduce required configuration and storage through service environment variables, secret files, and supported volumes. Use the actual container listening port rather than a Compose host-port mapping. Read `get_service_connection` and `get_service_environment` for real endpoints and credentials; replace Compose service names, localhost, and host-published ports with endpoints reachable from the agent or consuming service. Preserve secret flags and never expose credentials in output.
4. Start dependencies in their required order and verify readiness and connectivity with service status, bounded logs, and native client checks before starting dependent processes or migrations. Only after required session services are ready, configure the main application environment, run migrations as needed, and start the main application natively in the agent container. Verify its actual listening port and health endpoint. Replace agent setup/start/test commands that invoke Compose with native application commands using the provisioned services. Keep the Compose file for other environments when useful; it is an input to this translation, not an executable agent setup step.
5. Record service IDs and configuration so retries reuse the same session services. Explain any Compose behavior that the available service types cannot reproduce. Do not create duplicate dependencies, silently omit required components, or delete existing data to make setup pass.

These Compose replacements are session-bound for work in the agent environment. When the user explicitly requests a persistent project deployment, create or reuse separate regular services for the deployed application and its durable dependencies using the separate `deploymate` deployment skill; do not leave a production deployment dependent on services that suspend when the agent session closes.

### Example: Compose API, Postgres, and Redis

Given this Compose configuration (example credentials are illustrative only):

```yaml
services:
  api:
    build: .
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000
    ports: ["8080:8000"]
    environment:
      DATABASE_URL: postgres://app:example-only@db:5432/app
      REDIS_URL: redis://cache:6379/0
    depends_on: [db, cache]
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: example-only
    volumes: ["pgdata:/var/lib/postgresql/data"]
  cache:
    image: redis:7
volumes:
  pgdata:
```

Translate it as follows:

| Compose component | Agent setup destination | Configuration mapping |
| --- | --- | --- |
| `db` | Deploymate `postgres` service with `lifecycle="session"` | Match the required database/version where supported. Obtain actual database name, user, password, host, and port from service connection/environment tools. Map `pgdata` to supported session storage if persistence is required. |
| `cache` | Deploymate `valkey` service with `lifecycle="session"` | Confirm required Redis commands/modules are compatible. Use its real reachable endpoint and authentication settings; do not assume port 6379 or no password. |
| `api` (main application) | Native process in the agent container | Install the repository's locked Python dependencies and required native packages, then run `uvicorn app.main:app --host 0.0.0.0 --port 8000` using its environment/virtualenv. The application listens on 8000; Compose's host port 8080 does not apply. |

Execution order:

1. Discover supported creation schemas and resource plans; list existing services and reuse compatible session dependencies. Create only missing `db` and `cache` replacements with `create_service(lifecycle="session", ...)`, using actual schema fields and valid IDs.
2. Wait for both dependencies to be ready. Obtain their actual endpoints/credentials with `get_service_connection` and `get_service_environment`; verify connectivity from the agent container.
3. Set the main application's `DATABASE_URL` and `REDIS_URL` in its authorized local runtime environment using those returned values. Replace `db` and `cache` hostnames; never use the illustrative password above or assume Compose DNS exists. Keep secret values out of logs and version control.
4. Install/build the main application natively according to its lockfile and Dockerfile requirements, run any required migration command, and start the native command above in the agent container. Verify the application's configured health endpoint (for example `http://localhost:8000/healthz` when the repository implements it) and dependency access.
5. Record the reused/created session service IDs and native start command for subsequent setup/resume attempts. Do not record secret values in the summary.

Other common mappings: a Compose Node frontend that is the main application runs with the repository's native install/dev command in the agent container; a required separate queue worker can become a supported session worker service with the translated database/cache endpoints.
